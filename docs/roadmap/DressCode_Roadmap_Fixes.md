## ЧАСТЬ 1 — БАГИ (исправить первыми)

### 1.1 «Дней: 1/31» в прогнозе прошлых месяцев

**Проблема:** При просмотре прошлого месяца (например, февраля) в карточке филиала отображается блок «Прогноз до конца месяца: 0Р, Дней: 1/31 · тренд (1 раб.дн.)». Прогноз для завершённого месяца бессмысленен и путает пользователя.

**Причина:** API (строка 578 Код.gs) правильно возвращает `forecast: null` для прошлых месяцев. Но фронтенд (renderFilials) рендерит блок прогноза всегда, не проверяя значение.

**Что делать:**
- В `renderFilials()` (index.html) добавить проверку: если `f.forecast === null` или месяц < текущего — не рендерить блок прогноза
- Для прошлых месяцев вместо прогноза показывать итоговую строку: «Итог месяца: X₽ (Y% плана)»

**Где менять:** index.html → функция `renderFilials`, блок где генерируется HTML прогноза

### 1.2 «На счетах: нет данных» постоянно висит в шапке

**Проблема:** В правом верхнем углу дашборда отображается плашка «На счетах: нет данных» с кнопкой обновления. Она видна всегда и на всех вкладках.

**Причина:** Функция `updateBalanceBadge()` пытается отобразить баланс, но данные не загружаются (возможно, API для балансов не реализован или не настроен).

**Что делать (два варианта):**
- **Вариант А:** Скрыть плашку, пока данные балансов не подключены — `display: none` для элемента бэйджа
- **Вариант Б:** Подключить реальные данные балансов из Google Sheets (лист "БАЛАНСЫ")

**Где менять:** index.html → CSS стили бэйджа / функция `updateBalanceBadge`

### 1.3 Можно выбрать будущие месяцы без данных

**Проблема:** Селектор месяцев (`bizMonthSelect`) показывает все 12 месяцев, включая апрель–декабрь 2026. При выборе будущего месяца — все филиалы показывают 0Р без объяснения. Пользователь не понимает: данных нет, или бизнес действительно на нуле.

**Что делать:**
- Ограничить максимальный месяц текущим (март 2026 = месяц 3)
- Либо при нулевых данных показывать сообщение: «Данные за этот месяц ещё не внесены»
- При загрузке страницы — автоматически выбирать текущий месяц (сейчас так и есть, но стоит отключить будущие опции через `disabled`)

**Где менять:** index.html → генерация `<option>` для `bizMonthSelect`, или JS-код при загрузке вкладки Бизнес

---

### 1.4 Нет индикатора загрузки при смене месяца

**Проблема:** При переключении месяца данные подгружаются с API (2–5 секунд через Apps Script). Во время загрузки карточки филиалов просто исчезают, нет спиннера или сообщения «Загрузка...». Пользователь не понимает, идёт загрузка или произошла ошибка.

**Что делать:**
- При начале загрузки — показывать спиннер или текст «Загрузка данных...» в области карточек
- При ошибке — показывать сообщение с кнопкой «Повторить»
- При успехе — плавно показать карточки

**Где менять:** index.html → функция `loadBranches()`, добавить состояния loading/error/success в контейнер карточек

## ЧАСТЬ 2 — UX-УЛУЧШЕНИЯ

### 2.1 Мобильная адаптация (КРИТИЧЕСКИ ВАЖНО)

**Проблема:** В проекте 0 media queries. Viewport meta tag есть (`width=device-width, initial-scale=1.0`), но CSS не адаптируется под мобильные экраны. На телефоне (375px) всё мелко масштабируется. Учитывая, что владелец бизнеса скорее всего смотрит дашборд с телефона — карточки нечитаемые.

**Что делать — минимальная мобильная адаптация:**

```
@media (max-width: 768px) {
  /* Навигация */
  - иконки табов уменьшить или переделать в горизонтальную полосу

  /* Сводка по сети */
  - блоки Ателье/Химчистка/Всего — в одну колонку (сейчас 3 в ряд)
  - блоки Клиенты/Прибыль/Прогноз — в одну колонку

  /* Карточки филиалов */
  - полная ширина экрана
  - увеличить шрифт названия филиала
  - числа справа — увеличить размер

  /* Аналитика (модальное окно) */
  - полноэкранный режим на мобильных
  - графики — горизонтальный скролл при необходимости

  /* Селектор месяца */
  - увеличить размер, удобнее для тапа
}
```

**Где менять:** index.html → блок `<style>`, добавить в конец media queries

## ЧАСТЬ 3 — ОПТИМИЗАЦИЯ ПРОИЗВОДИТЕЛЬНОСТИ

### 3.1 Оптимизация API: один getValues() вместо 30 getValue()

**Проблема:** В `handleGetBranches()` (строки 567–569 Код.gs) для каждого филиала читаются 3 ячейки по одной: `sheet.getRange(row, col).getValue()`. Итого 10 филиалов × 3 = 30 отдельных вызовов к Sheets API. Каждый вызов — сетевой запрос, что замедляет ответ до 3–5 секунд.

**Что делать:**
- Перед циклом `FILIAL_MAP.forEach` — прочитать всю колонку одним запросом:
```javascript
var allData = sheet.getRange(1, col + 1, 260, 1).getValues();
// Теперь allData[row-1][0] даёт значение ячейки
```
- В цикле обращаться к массиву вместо sheet.getRange:
```javascript
var factA = parseFloat(allData[f.rowAtelie - 1][0]) || 0;
var factH = parseFloat(allData[f.rowHimch - 1][0]) || 0;
var factC = parseInt(allData[f.rowClients - 1][0]) || 0;
```
- Ожидаемое ускорение: с 3–5 сек до менее 1 сек

**Где менять:** Apps Script → Код.gs → функция `handleGetBranches`, строки 560–570

### 3.2 Кэширование API-ответов в localStorage

**Проблема:** Каждый раз при переключении месяца или обновлении страницы — полный запрос к Apps Script. Нет кэширования. При активном использовании можно упереться в квоты Apps Script.

**Что делать:**
- При получении данных от API — сохранять в localStorage с ключом `branches_month_X` и timestamp
- При загрузке — проверять кэш: если данные свежие (< 5 мин) — использовать кэш
- Для текущего месяца — TTL 5 минут
- Для прошлых месяцев — TTL 1 час (данные не меняются)
- Кнопка ↻ — принудительно обновлять минуя кэш

**Где менять:** index.html → функция `loadBranches`

### 3.3 Перенести PLAN_2026 и HISTORY_2025 из кода в Google Sheets

**Проблема:** Месячные планы (`PLAN_2026`) и исторические данные (`HISTORY_2025`) захардкожены в Apps Script (Код.gs). При изменении плана нужно редактировать код и деплоить новую версию API.

**Где менять:** Google Sheets (новые листы) + Apps Script → Код.gs → `getPlan2026()`, `HISTORY_2025`

## ЧАСТЬ 4 — ТЕХНИЧЕСКИЙ ДОЛГ

### 4.1 Разбить index.html на модули

**Проблема:** Один файл ~127KB содержит HTML + CSS + JS (96KB скриптов, 62 функции, 425 переменных). Любое изменение — работа с гигантским файлом. Нет разделения ответственности.

**Что делать (постепенно):**
- Вынести CSS в отдельный `styles.css`
- Вынести JS в `app.js` (или несколько файлов: `api.js`, `render.js`, `utils.js`)
- index.html — только разметка + подключение файлов
- Деплоить через GitHub Pages как и раньше (все файлы в одном репо)

**Приоритет:** Низкий. Делать после всех функциональных исправлений.

---

### 4.2 Заменить innerHTML на безопасные методы

**Проблема:** 22 использования innerHTML для рендера карточек. Хотя данные приходят из своего API, это плохая практика — потенциальный XSS-риск и хуже производительность.

**Что делать:**
- Постепенно заменять innerHTML на `createElement` + `textContent`
- Или использовать template literals + sanitization

**Приоритет:** Низкий. Делать при рефакторинге (пункт 4.1).

---

### 4.3 parseFloat || 0 маскирует ошибки данных

**Проблема:** Строки 567–569 Код.gs: если в ячейке текст или ошибка формулы, `parseFloat` вернёт NaN, `|| 0` заменит на 0. Данные потеряны, дашборд покажет «0» без индикации проблемы.

**Что делать:**
- Добавить проверку: если значение NaN и ячейка не пустая — логировать предупреждение
- В ответе API для таких филиалов добавить флаг `dataError: true`
- На фронте — показывать «⚠ ошибка данных» вместо «0Р»

**Приоритет:** Средний. Может помочь выявить проблему с химчисткой.
